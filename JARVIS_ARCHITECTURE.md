# JARVIS — универсальная архитектура

## 1. Главный диспетчер

Главный диспетчер — управляющий слой над всеми подсистемами. Он принимает задачу, определяет нужного специалиста, строит план, запускает инструменты, проверяет результат и возвращает пользователю итог.

Поток сложной задачи:

`цель → понимание → план → выбор специалиста/инструментов → выполнение → проверка → корректировка → итог`

## 2. Универсальное ядро

**JARVIS Core** — основной локальный мозг для обычного разговора, рассуждения, команд и планирования. Приоритет — бесплатная локальная модель пользователя, обозначенная в конфигурации как **Дракон**.

Точный Ollama/model tag не зашивается в код до его подтверждения. Поэтому приложение не подменяет «Дракона» Alama/Gemma/Qwen или другой моделью по догадке.

## 3. Специалисты

- **Vision** — анализ изображений, видео и экрана.
- **Code** — отдельный кодовый специалист, включая OpenCode-интеграцию.
- **Web Agent** — самостоятельная работа с интернетом, поиск, открытие страниц, сбор и сравнение данных.
- **Cloud LLM** — резервный/специализированный облачный интеллект, а не обязательная зависимость Core.

## 4. MCP — слой инструментов

MCP является отдельным транспортом/слоем подключения инструментов:

`браузер • файлы • Windows • GitHub • терминал • приложения • поиск • дополнительные сервисы`

Модель не получает прямой неконтролируемый доступ к Windows. Все действия проходят через реестр инструментов и защиту.

## 5. Память

Два уровня:

- кратковременная — текущий диалог и контекст задачи;
- долговременная — локальные факты, заметки, история и база знаний.

Архитектура допускает локальное векторное хранилище для семантического поиска по долговременной памяти. Существующие JSON memory/knowledge graph остаются рабочим базовым слоем.

## 6. Планировщик / Loop

Loop отвечает за многошаговые задачи. Он не просто генерирует ответ, а ведёт задачу до результата:

`цель → шаг → инструмент → результат → проверка → следующий шаг → финальная проверка`.

Например: «найди лучший вариант» означает собрать варианты, сравнить критерии, проверить источники/результаты и только затем сформировать ответ.

## 7. Защита действий

Обязательное подтверждение пользователя перед опасными действиями:

- удаление файлов;
- завершение процессов;
- установка программ;
- изменение системных настроек;
- отправка сообщений/почты;
- покупки и другие необратимые действия.

Без подтверждения такие операции не выполняются.

## 8. Голос — отдельный контур

Голосовой контур не является функцией LLM:

`два хлопка → активация → слушаю → STT → диспетчер/Core → TTS`

Важное требование — **barge-in**: если JARVIS говорит и пользователь начинает говорить, TTS немедленно прекращается, система переключается в режим слушания и ждёт новую фразу.

Активация хлопками, VAD, STT, прерывание TTS и TTS работают независимо от выбранной LLM.

## 9. 3D Visual Engine

Визуализатор — самостоятельный слой. Он получает события состояния от диспетчера и голосового контура.

Состояния отображаются по-русски:

`ОЖИДАНИЕ → СЛУШАЮ → РАССУЖДАЮ → ВЫПОЛНЯЮ → ОТВЕЧАЮ → ПОДТВЕРЖДЕНИЕ → ОШИБКА → ЗАВЕРШЕНИЕ`

Внутри визуального слоя:

`IR Core • аватар • контроллер • тело • жесты • глаза • трекинг • 3D-модель • лицо • lip-sync`

Аватар живёт постоянно даже без команды: дыхание, микродвижения, динамика нейронных связей и реакция на звук/системные события. Взгляд и микровыражения — **не включать** в текущую спецификацию.

## 10. Принцип работы

Ни один специалист не становится «главным мозгом» вместо диспетчера. Диспетчер управляет ролями; Core является главным локальным универсальным интеллектом; специалисты подключаются по необходимости; MCP даёт безопасный доступ к инструментам; память сохраняет контекст; Loop доводит сложные задачи до результата; голос и 3D являются независимыми интерфейсными контурами.
